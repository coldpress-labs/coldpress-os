# EventStream (§6.4)

> Before this protocol, a coldpress-os run leaves no machine-readable trace. Sacred docs capture intent, gate-eval JSONs capture decisions, but the *execution history* — which skill ran when, which gate evaluated with what outcome, which wave started and ended — vanishes once the session ends. This doc specifies the append-only event log that fills that gap.

**Source decision:** [tier3-positioning-brief-2026-04-22.md §5](../../../lab-hq-projects/hq-p001-coldpress-os/docs/tier3-positioning-brief-2026-04-22.md) — ports OpenHands' EventStream + Action/Observation/Condenser pattern as coldpress-os's execution-trace representation.

---

## The big picture

Every `coldpress` run — orchestrator invocation, interactive Butler session, or automated gate eval — writes events to:

```
.coldpress/runs/<run-id>/events.jsonl
```

One line = one event. Append-only. No updates, no deletes. Sequence numbers (`seq`) are monotonic and contiguous within a run.

**Complements, does NOT replace, the DAG plan.** The DAG says what the orchestrator *intends* to do; the EventStream records what *happened*.

**Not exposed to the LLM directly.** EventStream is for:
- **Debugging** — what did the orchestrator actually do last session?
- **Replay** — given the same inputs, reconstruct the trace.
- **Gate evaluation** — did a sacred doc get written before the gate evaluated?
- **Project Dashboard** (§6.10) — Stats tab reads skill-invocation counts, durations, success rates.

## Event families

### Actions — things the orchestrator DOES

| `kind` | When emitted | Key fields |
|--------|--------------|------------|
| `wave-start` | Wave begins | `wave_id`, `phase`, optional `label` |
| `wave-end` | Wave concludes | `wave_id`, `phase`, `status` (`success | failure | interrupted`), optional `duration_ms` |
| `skill-invoke` | Skill dispatched | `skill_id`, optional `caller` (subagent slug), optional `args` |
| `gate-evaluate` | Phase gate evaluation starts | `gate_id`, `phase` |

### Observations — results/responses

| `kind` | Pairs with | Key fields |
|--------|-----------|------------|
| `skill-result` | `skill-invoke` | `skill_id`, `cause_seq`, `exit_code`, optional `duration_ms`, `artifact_path`, `message` |
| `gate-pass` | `gate-evaluate` | `gate_id`, `phase`, `cause_seq` |
| `gate-fail` | `gate-evaluate` | `gate_id`, `phase`, `cause_seq`, `blockers[]` |

Observation events carry `cause_seq` pointing at the `seq` of the originating Action — readers reconstruct request/response pairs without inferring from adjacency. Skipped `cause_seq` means the Observation has no corresponding in-run Action (e.g., a skill invoked outside this run but whose result landed here).

### Meta event — Condensation

Emitted at wave boundaries by the orchestrator (Wave 6 follow-up work will wire this; Block DD ships the schema + persistence only). Turns each wave's exit summary into a first-class trace event — not implicit context compaction.

- `wave_id`, `summary` (≥1 char prose), `from_seq` + `to_seq` (inclusive range condensed).

## Common fields (every event)

| Field | Type | Notes |
|-------|------|-------|
| `schema_version` | `1` | Bumping requires a migration; readers reject unknown versions. |
| `seq` | integer ≥0 | Monotonic, contiguous within a run. `0, 1, 2, …`. Writer enforces. |
| `run_id` | kebab-case slug | Must match `/^[a-z0-9][a-z0-9-]*$/`. Generated by `makeRunId()`. |
| `timestamp` | ISO-8601 | UTC. Writer fills. |

`run_id` format from `makeRunId()`: `run-YYYYMMDD-HHMMSS-<6-hex>`. Lexicographic sort matches chronological order — `listRuns()` returns them in that order.

## The writer — `EventStreamWriter`

Single-writer-per-run abstraction at `src/event-stream/writer.ts`:

```ts
const w = await EventStreamWriter.open(projectDir, {
  runId: "run-20260424-150000-abcdef",   // optional; generator if omitted
});
await w.append({ kind: "wave-start", wave_id: "w-1", phase: 4 });
await w.append({ kind: "skill-invoke", skill_id: "create-prd", caller: "pm" });
await w.append({
  kind: "skill-result",
  skill_id: "create-prd",
  cause_seq: 1,
  exit_code: 0,
  artifact_path: "_context/sacred/prd.md",
});
await w.close();
```

Writer invariants:
- Fills `schema_version` / `seq` / `run_id` / `timestamp` automatically — caller supplies only the kind-specific fields.
- Validates against `EventSchema` before writing. Malformed input throws — the file never contains invalid lines.
- **Resumption-safe.** Re-opening a writer against an existing run reads the last line's `seq` and continues from `last + 1`. No duplicates.
- **Not concurrency-safe.** One writer per run at a time. Reader (e.g., dashboard) reads independently and doesn't hold a writer handle.

## The reader — `readRun` / `listRuns`

Pure functions at `src/event-stream/reader.ts`:

- `readRun(runId, { projectDir? })` → `Promise<Event[]>`
- `listRuns({ projectDir? })` → `Promise<string[]>` (lexicographic = chronological order)
- `assertSeqIntegrity(events)` — invariant check; throws on gap or duplicate

Error types (fail-loud; no silent skip):
- `EventStreamNotFoundError` — run dir or events.jsonl missing.
- `EventStreamParseError` — invalid JSON or schema-violating event. Carries line number for debugging.

Blank lines are tolerated (simplifies manual editing during dev). Any non-blank line must parse and validate.

## The CLI — `coldpress run`

```bash
coldpress run list
# run-20260424-150000-abcdef
# run-20260424-160012-123456

coldpress run inspect run-20260424-150000-abcdef
# #000 +     0ms ▶ WAVE  P4 w-1 — planning kickoff
# #001 +  5000ms → skill create-prd [by pm]
# #002 +150000ms ← skill create-prd exit=0 145000ms → _context/sacred/prd.md
# #003 +151000ms → gate  P4 phase-4-exit
# #004 +153000ms ✓ gate  P4 phase-4-exit
# #005 +154000ms ■ WAVE  P4 w-1 — success (154000ms)
#
# summary:  gate-evaluate=1  gate-pass=1  skill-invoke=1  skill-result=1  wave-end=1  wave-start=1    skills: 1✓ / 0✗  gates: 1✓ / 0✗
```

Options:
- `--time delta|absolute` — timestamp style. `delta` (default) shows `+Nms` from run start.
- `--no-colour` — strip ANSI.

Exit codes: `0` rendered (possibly empty), `2` run not found, `1` malformed stream / other error.

**No write-side CLI.** Event emission is an orchestrator-integration concern — `EventStreamWriter` is the programmatic API. Block DD ships schema + persistence + read-side CLI; **runtime wiring into skills + phase-gate evaluator is deferred to Wave 6 orchestrator follow-up work** (§6.5 checkpointer + later).

## Integration points

### Phase-7 security gate (§5.1)

When the orchestrator dispatches `aggregate-gate-results`, it can emit:

```
skill-invoke(skill_id: "aggregate-gate-results")
skill-result(skill_id: "aggregate-gate-results", exit_code, artifact_path: "_context/audit/security/aggregate-<date>.json")
gate-evaluate(gate_id: "phase-7-exit", phase: 7)
gate-pass | gate-fail(gate_id: "phase-7-exit", ..., blockers: [...])
```

The aggregator's pass/fail AND the gate-evaluation decision are both first-class trace events — reconstructible without running the skill again.

### Project Dashboard (§6.10) Stats tab

The dashboard's Stats tab reads `listRuns()` → `readRun()` per run → aggregates:
- Skill invocation counts (`skill-invoke` count, grouped by `skill_id`)
- Skill success rate (`skill-result` with `exit_code === 0` vs non-zero)
- Average skill duration (`duration_ms` histogram)
- Gate pass/fail ratio (across all runs)
- Current-run progress (latest run: `wave-start` and `wave-end` pairs per phase)

Read-only; dashboard never writes to the EventStream.

### `<NEED_INFO>` protocol (§5.4)

Future extension: add `need-info-emit` / `need-info-resolve` event kinds so NEED_INFO round-trips land in the trace. Not in Block DD's schema — ships when the orchestrator starts actually routing NEED_INFO emissions (Wave 6 follow-up).

## What's NOT in this protocol

- **Runtime wiring into skills / subagents.** Block DD ships the persistence substrate. Orchestrator follow-up work (§6.5 checkpointer etc.) wires actual event emissions from skill execution.
- **Snapshot / rewind.** `seq` is monotonic but we don't persist intermediate artefact state alongside — rewinding to `seq=N` doesn't restore the filesystem. Snapshots are a §6.5 concern (LangGraph checkpointer).
- **Cross-run correlation.** Each run is self-contained. No `parent_run_id`; no run-tree.
- **Event deletion / GC.** Runs accumulate. A future housekeeping skill might prune runs older than N days; not in Block DD.
- **Concurrent writers.** One writer per run. Multi-writer would need leader election or a separate log-shipping layer; not needed for v1.
- **Streaming consumption.** Readers load the whole file. For large runs (>10k events), add incremental `tail` support in a follow-up; not needed for current corpus sizes.

## Extending

### Adding a new event kind

1. Author a new Zod schema in `schemas/event-stream.schema.ts` following the `EventBaseSchema.extend({...})` pattern.
2. Add to the `EventSchema` discriminated union.
3. Update the `renderBadge` + `renderBody` branches in `src/event-stream/inspect.ts`.
4. Add a row to the "Event families" table above.
5. Test the new kind in `test/event-stream.test.ts`.

### Bumping `schema_version`

Breaking change. Needs:
1. New literal `schema_version: 2` in the base.
2. Reader migration shim (accept `1` or `2`, upgrade `1` in-memory to `2`).
3. DECISIONS-LOG entry.
4. Deprecation horizon for v1 readers.
