# Graph Schema

> Coldpress-os's knowledge graph is built by [Graphify v4](../graph/vendor/graphify/) and serialised as NetworkX node-link JSON. This doc specifies the shape — the base Graphify format plus the coldpress-os-specific extensions for sacred-doc governance, environment tagging, and secure-manifest handling.

**Runtime artefact:** `<project>/.coldpress/graph/graph.json` (git-ignored; regenerated by `coldpress graph rebuild`).

**Source code:** [`src/graph/types.ts`](../src/graph/types.ts), [`src/graph/index.ts`](../src/graph/index.ts).

**Schema change protocol:** bumping `schema_version` is a breaking change — consumers (skills, Butler queries) must be updated in the same wave. Additive changes (new optional node/edge fields) don't require a version bump.

---

## 1. Top-level shape

```jsonc
{
  "directed": false,          // NetworkX flag — coldpress-os uses undirected graphs today
  "multigraph": false,        // single edge per (src, tgt, relation) tuple
  "graph": { },               // graph-level metadata (project_slug, generated_at, schema_version)
  "nodes": [ /* ... */ ],     // array of Node objects (see §2)
  "links": [ /* ... */ ]      // array of Edge objects (see §3) — NetworkX calls edges "links" in node-link format
}
```

The `directed` / `multigraph` / `graph` / `nodes` / `links` keys are NetworkX's native node-link contract. Coldpress-os adds conventions inside the `graph` metadata and node/edge objects — see below.

## 2. Node types

Every node inherits a base shape from Graphify; coldpress-os extends it with `coldpress` metadata.

### 2.1 Base Graphify node

```jsonc
{
  "id": "client_baseclient",              // stable unique identifier
  "label": "BaseClient",                  // human-readable display name
  "file_type": "code",                    // "code" | "doc" | "image" | "video"
  "source_file": "src/auth/client.py",    // project-relative path
  "source_location": "L31",               // line number reference in source_file
  "community": 2                          // Leiden community id (dense cluster)
}
```

### 2.2 Coldpress-os extensions

Coldpress-os adds a `coldpress` namespace object to each node for framework-aware semantics. These fields are optional (some come only from adapters we ship on top of Graphify).

```jsonc
{
  "id": "...",
  "label": "...",
  "file_type": "code",
  "source_file": "_context/sacred/prd.md",
  "source_location": "L42",
  "community": 3,

  "coldpress": {
    "node_type": "SacredDoc",             // see §2.3 — coldpress-os node taxonomy
    "env_tag": "sandbox",                  // see §2.4 — environment tagging
    "dir_role": "_context/sacred",        // see §2.5 — directory semantic
    "governance": {                        // only present for SacredDoc nodes
      "change_workflow": "prd-change",
      "version": "1.0"
    }
  }
}
```

### 2.3 `node_type` values (coldpress-os taxonomy)

| `node_type` | Description | Typical `source_file` |
|-------------|-------------|-----------------------|
| `Document` | Prose markdown, not sacred | `_context/planning/*.md`, `_context/design/*.md` |
| `SacredDoc` | Governed sacred document | `_context/sacred/{context,tech-stack,prd,architecture}.md` |
| `Artefact` | Structured output with schema | `_context/tracking/sprint-status.yaml`, `_context/audit/*.md` |
| `CodeModule` | File-level code unit | `src/**/*.{ts,py,go,...}` |
| `CodeSymbol` | Intra-file symbol (class, function, method) | derived from `source_file` + `source_location` |
| `CredentialName` | Name (never value) from `secure/manifest.yaml` | `secure/manifest.yaml` |
| `Input` | Material fed into the project | `_input/**` |

Nodes without a `coldpress.node_type` fall back to Graphify's native `file_type` classification — `code`, `doc`, `image`, `video`.

### 2.4 `env_tag` values

Three-tier pattern tagging. Required on every node that resolves to a file under `sandbox/` or `live/`; optional elsewhere.

| `env_tag` | Meaning |
|-----------|---------|
| `sandbox` | Lives under `sandbox/` — development copy, may be iterated freely |
| `live` | Lives under `live/` — production copy, governance-protected |
| `both` | Same content exists in both — useful for promoted artefacts |
| `neither` | Lives outside sandbox/ and live/ (planning docs, sacred docs, inputs) |

### 2.5 `dir_role`

The coldpress-os directory the node lives under — used by query-side filters to scope a query to a specific role (e.g., "only sacred docs" or "only audit artefacts"). Matches the top-level folder taxonomy: `_context/sacred`, `_context/planning`, `_context/design`, `_context/implementation`, `_context/testing`, `_context/tracking`, `_context/handoffs`, `_context/audit`, `_input/raw`, `_input/legacy`, `_input/reference`, `_input/vendor`, `_input/assets`, `secure`, `sandbox`, `live`, other.

## 3. Edge (link) types

### 3.1 Base Graphify edge

```jsonc
{
  "source": "client_baseclient",          // NetworkX edge endpoint — node.id
  "target": "client_timeout",             // NetworkX edge endpoint — node.id
  "_src": "client_baseclient",            // Graphify internal alias (kept for compat)
  "_tgt": "client_timeout",
  "relation": "imports_from",             // edge type — see §3.3
  "confidence": "EXTRACTED",              // "EXTRACTED" | "INFERRED" | "MANUAL"
  "source_file": "src/auth/client.py",    // where this edge was observed
  "source_location": "L6",
  "weight": 1.0                           // numeric weight for community detection
}
```

### 3.2 Coldpress-os relation taxonomy

Graphify ships a general `relation` field; coldpress-os standardises to these values:

| `relation` | Semantics | Typical source / target |
|-----------|-----------|-------------------------|
| `imports_from` | Code import / include dependency | CodeModule → CodeModule |
| `calls` | Intra-code call relationship | CodeSymbol → CodeSymbol |
| `references` | Prose mentions another artefact | Document → Document / SacredDoc / CodeModule |
| `descends_from` | Derivation / inheritance | Document → SacredDoc (story descends from PRD; architecture descends from PRD) |
| `implements` | Code implements a spec | CodeModule → SacredDoc (implementation story implements PRD) |
| `tests` | Test covers a target | CodeModule (test) → CodeModule (production) |
| `deploys_to` | Deployment target dependency | CodeModule → env node |
| `promoted_from_sandbox` | Live copy was promoted from sandbox | live file → sandbox file |
| `superseded_by` | Older artefact replaced by newer | prior version → current version |
| `consumes` | Input adapter relationship | Input → (whatever it feeds) |

### 3.3 `confidence` values

- `EXTRACTED` — direct observation from static analysis (AST, imports).
- `INFERRED` — derived by Graphify's semantic pass (e.g., cross-file reference based on naming).
- `MANUAL` — added via the `coldpress graph annotate` command (future). Never overwritten by rebuilds.

## 4. Graph-level metadata

The top-level `graph: {}` object carries coldpress-os-specific metadata:

```jsonc
{
  "graph": {
    "schema_version": 1,
    "project_slug": "my-project",
    "generated_at": "2026-04-23T20:00:00Z",
    "graphify_version": "0.4.27",
    "coldpress_version": "0.2.0-alpha",
    "counts": {
      "nodes": 144,
      "links": 330,
      "communities": 8
    }
  }
}
```

**`generated_at`** is not treated as a source-of-truth field by the drift check — the file is regenerated on every `coldpress graph rebuild`. If you need reproducibility (CI-driven graph diff), pin the input corpus and accept that timestamps will differ.

## 5. Exclusions — the secure-manifest rule

**Credential VALUES are never indexed.** Only credential NAMES from `secure/manifest.yaml` land as `CredentialName` nodes. Contents of `secure/.env*` are excluded at adapter time — they never reach the graph.

The secure-manifest adapter's contract:

- Reads `secure/manifest.yaml`.
- For each key declared, emits one `CredentialName` node with `label = "OPENAI_API_KEY"` (or whatever the declared name is).
- Emits edges `(CodeModule) → (CredentialName)` where the code module references the env var.
- Never reads `secure/.env*`. Never puts a value in a node attribute or edge. A test case verifies credential values are absent from the emitted graph.

If `secure/.env*` is git-tracked by mistake, the pre-commit hook at `scripts/check-secrets.sh` catches it before it reaches this indexer. Defense in depth.

## 6. Sizes and performance expectations

On a 10kLOC TypeScript codebase (representative coldpress-os consumer):

| Measure | Expected |
|---------|----------|
| Nodes | ~500–2,000 |
| Edges | ~1,000–5,000 |
| Communities | ~10–30 |
| Graph file size | 100 KB – 1 MB JSON |
| Rebuild time | ~5–30 seconds (dominated by Python startup + tree-sitter parsing) |
| `Graph.load()` time (Node-side) | <100 ms (JSON parse) |
| Typical query traversal | <50 ms (in-memory BFS / DFS) |

For corpora larger than ~10k nodes, the in-memory representation starts costing real RAM and the naïve traversals get slow. That's the point at which the **optional SQLite + sqlite-vec layer** (plan §3.7) earns its keep — FTS5 queries over node labels, recursive CTEs for deep traversal, vector search for semantic retrieval. Shipping that layer is deferred to post-v0.3 per plan; JSON + in-memory is sufficient for v0.3.

## 7. Versioning and migration

`graph.schema_version: 1` today. Breaking changes bump to `2`:

- Renaming a `relation` value.
- Removing a `node_type`.
- Changing the shape of `coldpress.governance`.

Additive changes (new optional field, new `node_type` value, new `relation` value) are backward-compatible — consumers that don't know the new value ignore it gracefully. Prefer additive over breaking wherever possible.

On schema version mismatch, `Graph.load()` fails loudly with a clear migration hint — no silent degradation. User runs `coldpress graph rebuild` to regenerate against the current schema.

## 8. Extending

### New `node_type`

1. Add to the enum in [`src/graph/types.ts`](../src/graph/types.ts).
2. Update the taxonomy table in §2.3 above.
3. Add adapter logic in the relevant indexer (Wave 3 Block O).
4. Document test coverage in `test/graph.test.ts`.

### New `relation`

1. Add to the enum in `src/graph/types.ts`.
2. Update the relation taxonomy in §3.2 above.
3. Extend the indexer that emits the relation.
4. Update consumers (skills that filter by relation) — typically an additive change if they use a fall-through default.

### New graph-level field

Additive: add to the Zod schema in `src/graph/types.ts`, document here, ship.
