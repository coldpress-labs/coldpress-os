# Glossary — coldpress-os

> Terminology used across the framework. Alphabetical order.

---

| Term | Definition |
|------|-----------|
| **A/P/C Menu** | The standard navigation options in step-file workflows: Advanced (go deeper), Party Mode (multi-agent perspectives), Continue (next step). |
| **Butler** | The main Claude Code session that orchestrates subagents. Not a subagent itself. Butler reads CLAUDE.md and .claude/SYSTEM.md, routes work to subagents, and synthesizes results. The user-facing name is set by `butler.display_name` in `coldpress.yaml` (default `"Butler"`); the framework-internal role is always Butler regardless of display name. |
| **`butler.display_name`** | Optional field in `coldpress.yaml` under `butler:` — the label the user sees Butler address itself by. Defaults to `"Butler"`. Substituted into CLAUDE.md + .claude/SYSTEM.md self-references at init; can be renamed by the user during Phase 1 `intake` Step 4. |
| **Cascade** | The process of updating all downstream artifacts when a sacred document changes. |
| **coldpress.yaml** | The single project configuration file that coldpress-os reads. Lives at project root. Includes agent mode configuration. |
| **DAG** | Directed Acyclic Graph — used by the orchestrator to model task dependencies for parallelization. |
| **Dispatch** | The act of Butler delegating work to a subagent. Butler constructs a task prompt with context, file paths, and mode, then the subagent runs independently. |
| **Governance** | The rules protecting sacred documents from uncontrolled changes. See `governance/sacred-docs.md`. |
| **Halt-at-Menu** | The step-file rule requiring agents to stop and wait for user input when presenting options. |
| **Handoff Artifact** | A `_handoff.md` file summarizing decisions, open questions, and constraints when work transfers between subagents. Stored in `_context/handoffs/`. |
| **`intake`** | Phase 1 lifecycle skill. Steps: material solicitation (walks the 5 `_input/` subfolders with the user), shape determination (greenfield/brownfield), intent seed (writes `_context/sacred/context.md` with a one-sentence intent + `status: seed`), working mode (preferred IDEs, cadence, team shape, Butler's display name → `coldpress.yaml`), and gate-and-route (runs Phase 1 exit gate + hands off to `@analyst`). Re-runnable: Step 1 can re-enter from a later phase to ingest new material without corrupting active-phase state. |
| **`_context/`** | Top-level project folder holding produced artefacts. Eight canonical subfolders: `sacred/`, `planning/`, `design/`, `implementation/`, `testing/`, `tracking/`, `handoffs/`, `audit/`. See `docs/phase-subfolder-mapping.md`. |
| **`_input/`** | Top-level project folder holding material fed *into* the project: `raw/`, `legacy/`, `reference/`, `vendor/`, `assets/`. Parsed documents land at `_input/.parsed/`. Distinct from `_context/` which holds produced artefacts. Each subfolder ships with a README explaining its purpose; Phase 1 `intake` walks all five during material solicitation. |
| **`_input/assets/`** | The 5th `_input/` subfolder — client-provided visual and brand material: logos, brand guidelines, Figma exports, design tokens, images, fonts. Added in Phase II Part 1 Wave 1. Distinct from `_input/reference/` (optional inspiration) and `_input/vendor/` (required third-party integration docs). |
| **`audit/` (subfolder)** | `_context/audit/` — backward-looking artefacts: retrospectives, code reviews, security scans, deployment-readiness reports, ops health checks. |
| **Handoff (typed)** | A high-stakes inter-phase artefact carrying a `.meta.json` sidecar validated by a Zod schema. Two handoffs qualify today: PRD→architecture, stories→implementation. See `docs/handoff-registry.md`. |
| **Lifecycle Phase** | One of 11 sequential stages under **Shape A** (v0.3.0-alpha): Bootstrap, Discovery, Tech Stack, Planning, **Design**, **Architecture**, Breakdown, Implementation, Deployment, Operate, Evolve. Phase 11 (Evolve) is final; closure feeds the next iteration's Phase 1. Old Phase 4 (Planning) was split into Phase 4 (PRD-only) + Phase 5 (Design) + Phase 6 (Architecture); old phases 5–9 cascade-renamed to 7–11. |
| **Hello Butler** | The canonical way to start (or resume) any coldpress-os session. Typing `Hello Butler` triggers `orient` (state-detect) which routes to `let's begin` (fresh project → runs `intake`) or `where are we` (returning session → reads `.coldpress/local-config.yaml` + latest handoff to report current phase + open items). See [`butler.md`](butler.md). |
| **Shape A** | The 11-phase lifecycle shape introduced in v0.3.0-alpha. Expands Spec → Plan → Implement → Review by separating Design (Phase 5) from Architecture (Phase 6), adding `@reviewer` for Phase 11 Evolve and `@devops` for Phases 9–10. Adds the forward-carry quartet (design / architecture / implementation / ops deltas) and the silent-divergence guard at P5 → P6. Alternative shapes (B, C…) are not currently implemented; the name preserves future flexibility. |
| **Forward-carry quartet** | The four delta instances added in Shape A that carry late-surfacing constraints across phase boundaries: design-deltas (P5 exit), architecture-deltas (P7 entry), implementation-deltas (P11 batch), ops-deltas (P11 retrospective). Each resolves via four options: `accept_into_prd`, `reject`, `flag_for_architecture_ADR`, `park_for_phase_11`. |
| **Silent-divergence guard** | The structural guarantee at the Phase 5 → Phase 6 boundary that design intent and architecture cannot drift silently. Phase 5 design-deltas flagged `flag_for_architecture_ADR` become REQUIRED ADRs at the Phase 6 exit gate; missing the ADR fails the gate. New in Shape A v0.3.0-alpha. |
| **Multi-Agent Orchestration** | The pattern where Butler dispatches work to independent subagents, each with their own context window, tools, and model. |
| **Mode** | A subagent operating configuration set in `coldpress.yaml` and passed by Butler. Examples: developer (standard/quick), verifier (rapid/strategic), analyst (discovery/brief/creative/strategic). |
| **`orient`** | Phase 1 lifecycle skill Butler runs at the start of every session until Phase 1 is complete. Four cheap, read-only steps: mode detect (first-session / re-entry / resume), greeting (first session only), scaffold sanity check, lifecycle intro (skippable). Hands off to `intake`. If a prior session set `needs_graph_rebuild: true`, orient Step 1 surfaces the error and offers a retry. |
| **Progressive Disclosure** | Loading one step-file at a time rather than the entire workflow. Reduces context load and prevents skipping. |
| **Promotion** | Copying validated application code from devSandbox to the production app repo. Planning artifacts never promote. |
| **`personas`** | Phase 2 workflow skill (`@ux-designer`). Produces canonical UX research artefacts: user archetypes, journey maps, accessibility/device/locale targets. Tier 1 methods: User Interviews, Empathy Mapping, Jobs to be Done, Journey Mapping, Diary Studies, Affinity Clustering. Output: `_context/planning/personas-{date}.md`. |
| **`constraint-research`** | Phase 2 workflow skill (`@analyst`). Defines the binding constraint envelope that Phase 3 tech-stack decisions must honour — compliance, protocols, performance floors, accessibility levels. Explicitly NOT a technology-comparison skill (that's Phase 3). Outputs `_context/planning/research/constraint-{topic}-{date}.md`. |
| **Supersede pattern** | The framework convention for recording when a Phase 2 discovery finding contradicts material in `_input/`. When confirmed by the user, the `promptSupersede` helper (`src/governance/supersede.ts`) writes a `superseded_by` graph edge from the `_input/` file to the sacred doc, adds the `_input/` path to the sacred doc's `supersedes:` frontmatter array, and appends a row to `_context/audit/supersessions-{date}.md`. Idempotent: re-invocation with the same source/target pair is a no-op. |
| **Supersessions log** | Append-only markdown table at `_context/audit/supersessions-{date}.md`. One row per confirmed supersession. Columns: Entry ID, Date, Sacred Doc, Superseded `_input/` file, Rationale, Context. Never edited in-place; reversals add a new row with a reference to the original. See `docs/supersessions-log-spec.md`. |
| **Validated distillate (second)** | `stack-selection-summary-v{N}.md` is the second validated distillate in the lifecycle. The first is `product-brief-v{N}.md` (Phase 2). Both are non-sacred, versioned, regeneratable summaries derived from richer upstream artefacts. Both must validate against a distillate schema with `regeneratable: true` (const). Subsequent phases follow the same pattern: each phase that produces a summary document produces one more distillate. |
| **Warm handoff** | The Phase 2 convention of reading Phase 1 `intake` outputs (`_context/sacred/context.md` seed, `.coldpress/local-config.yaml` conditions, `.coldpress/graph/graph.json`) rather than asking the user to re-state what intake already captured. Contrast with cold-start (pre-intake-era) where every phase began with open-ended questions. Implemented via condition-reader (`src/orchestration/condition-reader.ts`) + graph-staleness check (`src/graph/staleness.ts`). |
| **6-dimension rubric** | The evaluation framework used by `stack-evaluation` to score each technology candidate: (1) fit — how well it solves the core requirement; (2) cost — licensing, hosting, API fees vs project budget; (3) team_familiarity — how well the team knows the technology; (4) ecosystem_maturity — community size, libraries, long-term support; (5) lock_in — vendor dependency and exit cost; (6) vibe_fit — how well it matches the project's tone and the builder's workflow. Each dimension scored 0–10; a `weighted_total` aggregates them. Rubric data is not persisted — only the final ADR is written. |
| **Commit-point pattern** | The framework convention identifying Phase 3 stack-lock as the point after which pivoting becomes expensive. Mirrors Phase 2's validate-idea Step 9 escape hatch but for the build (not the idea). Three deliberate surfacings: Phase 3 entry, Step 3a red-flag, Step 5a baselines confirmation. After lock, changes go through governance/tech-stack-change/workflow.md. |
| **Pre-lock red-flag escape hatch** | Step 3a of the `stack-locking` skill — a structured pause before writing `tech-stack.md` sacred. If Butler surfaces critical risks (lock-in, cost concerns, unresolved ADRs), the user can proceed, revise, or invoke party-mode. Mirrors `validate-idea` Step 9. Outcome logged to `_context/audit/stack-lock-decisions-{date}.md`. |
| **Sacred-doc change-workflow** | The governance path for amending a sacred document after user signoff. Each sacred doc has its own change-workflow in `governance/change-workflows/` (e.g., `context.md` changes → `governance/change-workflows/context.md`). Distinct from and complementary to the supersede-check pattern: change-workflow fires post-signoff for intentional amendments; supersede-check fires pre-signoff for `_input/` conflicts. |
| **Supersede-check precedence** | The rule clarifying when supersede-check vs sacred-doc change-workflow applies: supersede-check fires *during authoring* (before `context-sacred-signoff`) when user answers contradict `_input/` claims; change-workflow fires *after signoff* for intentional amendments. The two mechanisms compose — a Phase 4 decision that overrides a `context.md` claim would invoke the change-workflow AND could fire a supersede-check for the `_input/` document the context.md originally referenced. See `lifecycle/2-discovery/README.md` §Architectural Note. |
| **Sacred Document** | A foundational project artifact (context.md, tech-stack.md, PRD, architecture.md) protected by change workflows. |
| **Skill** | The atomic unit of work in coldpress-os. Self-contained with step-files and references. See `skills/_schema.md`. |
| **Stack Pack** | A pluggable, archetype-keyed set of skills for a project type (e.g., `vibe-coder-fullstack`, `static-multipage-blog`, `cli-npm-publishable`). Each pack declares `archetype_fits` (product-type × domain-complexity × functional-profile), `pre_picked` technology choices, `baselines_out_of_box`, and a `quickstart_skill`. Packs are starting points — individual decisions can be overridden. Described by `pack.yaml` at the pack root, validated against `schemas/pack.schema.json`. |
| **Stack-pack discovery** | The process in `stack-discovery-sync` Step 2b where Butler scores available packs against the project's archetype signals (product-type, domain-complexity, team-shape, functional-profile from Phase 2 evidence). Packs with score ≥ 0.7 are proposed as strong match; 0.4–0.7 as partial match; < 0.4 as no-match → independent evaluation. |
| **`stack-discovery-sync`** | Phase 3 entry skill (`@architect`). Consolidates Phase 2 evidence, classifies the project archetype, matches against the stack-pack library, and derives a tiered shortlist per decision-area (T1 pack pre-pick / T2 catalog / T3 independent). Outputs `_context/planning/stack-shortlist-v{N}.md`. Runs once at Phase 3 entry — downstream skills do not repeat this consolidation. |
| **`stack-shortlist`** | Planning artefact produced by `stack-discovery-sync`. Three sections: (1) pack-match verdict (matched pack name, score, user confirmation, uncovered areas); (2) per-decision-area tiered candidates (T1/T2/T3 with rationale); (3) baselines-applicability (how each baseline category is covered by the matched pack). Schema-validated against `schemas/planning-artefacts/stack-shortlist.schema.json`. |
| **`stack-selection-summary`** | The second validated distillate in the lifecycle (first is `product-brief`). Produced by `stack-locking`. Captures the final stack decisions in a brief, regeneratable summary. Schema requires `regeneratable: true` (const). Lives at `_context/planning/stack-selection-summary-v{N}.md`. Validated against `schemas/distillates/stack-selection-summary.schema.json`. |
| **Step-File** | A single-step Markdown file in a multi-step workflow. See `docs/step-file-spec.md`. |
| **Story Graph** | The story dependency DAG authored by the `story-graph` skill in Phase 7 Breakdown, serialised to `_context/implementation/story-graph.yaml`. `coldpress waves` computes waves, critical path, and schedule over it. Replaced the PERT chart in v0.4. |
| **Subagent** | An independent Claude Code instance with its own context window, tools, and model. Defined in `.claude/agents/`. Dispatched by Butler, returns results to Butler. Cannot call other subagents directly. |
| **Task Prompt** | The context Butler constructs when delegating to a subagent — includes the user's request, relevant file paths, prior decisions, mode, and constraints. |
| **Thin Wrapper** | A 3-line `.claude/skills/` entry that points to the canonical skill in the coldpress-os submodule. |
| **Three-Tier Pattern** | Project structure: local root (credentials) → devSandbox (all dev) → app (production only). Pattern A. |
| **Valet** | Butler's meta counterpart — the framework evolution subagent. Proposes changes to coldpress-os via GitHub Issues/PRs. Operates outside the normal lifecycle. |
| **Wave** | A group of tasks that can execute in parallel, determined by topological sorting of the DAG. |
